# Dashboard Artifact Contract

## 1. Goal

This contract defines how the management system builds, previews, saves, and publishes dashboards generated by the Coding Agent while preserving the freedom required for Vibe Coding within `src/`.

Core principle:

> The management system constrains dashboard inputs, outputs, and security boundaries, not the internal implementation of `src/`.

Dashboard source code is a first-class artifact. It is not converted into a low-code DSL and does not have to map to a fixed chart component tree.

## 2. Coding Agent Experience That Must Be Preserved

The Coding Agent has full control over `src/**` and may:

- Create, delete, move, and rename files.
- Freely split components, Hooks, utilities, and styles.
- Freely choose page layouts and information hierarchy.
- Use CSS, SVG, Canvas, WebGL, and native browser APIs.
- Use platform-provided component and visualization libraries.
- Implement filters, linked views, drill-downs, animations, and custom interactions.
- Continuously refactor existing implementations through conversation instead of being limited to editing JSON configuration.

The management system must not:

- Require every chart to be declared in the Manifest.
- Convert `src/` back into a proprietary platform DSL.
- Rewrite Agent-generated source through a visual editor.
- Depend on parsing the React component tree to understand the dashboard.
- Prescribe a fixed component count, directory hierarchy, or page layout.

The management system cares only about:

1. Whether the dashboard builds successfully.
2. Whether the dashboard uses valid data queries.
3. Whether the dashboard complies with runtime and security boundaries.
4. Where the build artifact entry point is located.

## 3. Directory Structure and Ownership

```text
dashboard/
├── dashboard.manifest.json
├── src/
├── public/
├── package.json
├── vite.config.ts
└── dist/
```

| Path | Owner | Description |
|---|---|---|
| `src/**` | Coding Agent | Complete freedom to generate and refactor |
| `public/**` | Coding Agent | Local images, fonts, and other static assets |
| `dashboard.manifest.json` | Coding Agent + platform validation | Declares the external contract, not internal UI |
| `package.json` | Platform | Fixed scripts and approved dependencies |
| `vite.config.ts` | Platform | Fixed build and Runtime injection behavior |
| `dist/**` | Build system | Must not be edited directly by the Agent |

The first version must not allow the Agent to modify `package.json` directly or install arbitrary dependencies. The platform should provide sufficiently general dependencies without restricting how `src/` is organized or implemented.

If a real need emerges later, add an explicit `request_dependency` workflow in which the platform reviews and updates the dependency template instead of allowing arbitrary `bun add` commands.

## 4. Manifest Boundary

The Manifest describes only the external dependencies the management system must understand. It does not describe page layout or chart implementation.

First-version example:

```json
{
  "schemaVersion": 1,
  "title": "Sales Analysis",
  "description": "Shows sales trends and regional performance",
  "sourceEntry": "src/main.tsx",
  "entry": "dist/index.html",
  "runtimeVersion": "1",
  "queries": [
    {
      "id": "monthly-sales",
      "parameters": {
        "startDate": "date",
        "endDate": "date"
      }
    },
    {
      "id": "region-ranking",
      "parameters": {}
    }
  ]
}
```

### 4.1 Fields

| Field | Required | Description |
|---|---|---|
| `schemaVersion` | Yes | Manifest Schema version |
| `title` | Yes | Dashboard display name |
| `description` | No | Description of the dashboard's purpose |
| `sourceEntry` | Yes | Agent-chosen JavaScript or TypeScript module under `src/` imported by the fixed build shell |
| `entry` | Yes | Entry file produced by the build; fixed to `dist/index.html` in Runtime version 1 |
| `runtimeVersion` | Yes | Dashboard Runtime API version |
| `queries` | Yes | Registered Query IDs the page may call and their parameter types |

### 4.2 The Manifest Explicitly Excludes

- Chart types.
- Chart positions and dimensions.
- Grid layouts.
- Component trees.
- CSS tokens and color configuration.
- Page state-management choices.
- SQL, database URLs, or credentials.
- React components, Props, or internal events.

All of these are determined by `src/`.

## 5. Runtime API

Generated code must not connect directly to databases or hold access tokens. It queries data and reads runtime context through the platform-provided Runtime SDK.

Proposed interface:

```ts
interface DashboardRuntime {
  query<T extends Record<string, unknown> = Record<string, unknown>>(
    queryId: string,
    parameters?: QueryParameters,
    options?: QueryOptions,
  ): Promise<QueryResult<T>>;

  watch<T extends Record<string, unknown> = Record<string, unknown>>(
    queryId: string,
    parameters: QueryParameters | (() => QueryParameters),
    options: QueryWatchOptions,
    listener: (event: QueryWatchEvent<T>) => void,
  ): QueryWatcher;

  getContext(): Promise<DashboardContext>;
  ready(details?: { title?: string }): void;
  reportError(error: unknown): void;
}

interface DashboardContext {
  locale: string;
  timezone: string;
  theme: "light" | "dark";
  mode: "preview" | "published";
}
```

The complete refresh, cancellation, freshness, and watcher contract is defined in `docs/live-data-and-refresh-contract.md`.

The Agent uses it through a fixed module in source code:

```ts
import { dashboard } from "@mda/dashboard-runtime";

const result = await dashboard.query("monthly-sales", {
  startDate: "2026-01-01",
  endDate: "2026-03-31"
});

const watcher = dashboard.watch(
  "monthly-sales",
  () => ({ startDate, endDate }),
  { intervalMs: 30_000, pauseWhenHidden: true, refreshOnFocus: true },
  handleQueryEvent
);
```

The SDK may use iframe `postMessage` under the hood to communicate with the host. The host attaches the current viewer identity and forwards requests to the Data Gateway. Generated code must never receive raw database credentials or management-application login tokens.

The Runtime API is a stable boundary, but it does not prescribe how the Agent wraps or consumes it within `src/`. A published frontend bundle is immutable, while `query()` and `watch()` continue retrieving current authorized source data without invoking Pi.

## 6. Query Contract

The Manifest stores only Query IDs and parameter types. SQL or API request definitions remain in the Data Gateway and are not included in frontend artifacts.

Call flow:

```text
src code
  → dashboard.query(...) or dashboard.watch(...)
  → iframe host
  → Data Gateway
  → authorization
  → registered query
  → data source
```

Publishing must confirm that:

- The Query ID exists.
- The current dashboard is authorized to use the Query.
- Parameter names and types match.
- The Query is valid for the publishing context and its viewers.

Filters, linked interactions, and data transformation within the page remain freely implemented by `src/`.

## 7. Build Contract

The platform-owned `packages/dashboard-template` build shell accepts an Agent-chosen `sourceEntry` under `src/` and specifies only one conceptual command and one output:

```bash
bun run build
```

A successful build must produce:

```text
dist/index.html
```

Other than the entry point and Runtime injection, the platform places no requirements on the internal Bundle structure.

Within `src/`, the Agent may use:

- Single-page or multi-view structures.
- Any component decomposition.
- CSS Modules, plain CSS, or platform-provided styling solutions.
- Platform-provided ECharts, D3, Canvas, and similar capabilities.
- Custom SVG, charts, and interaction implementations.

Whether the implementation uses React Router, a global state library, or another organizational approach is outside the Artifact Contract.

## 8. Validation Contract

`validate_dashboard` validates boundaries only. It does not judge code style or page implementation choices.

It must validate that:

1. `dashboard.manifest.json` conforms to its Schema.
2. `bun run build` succeeds.
3. `dist/index.html` exists.
4. Every Query ID in the Manifest exists and is authorized.
5. Query parameters match their definitions.
6. No unapproved dependencies are used.
7. Source code contains no obvious hard-coded secrets.
8. The page declares no prohibited external network destinations.
9. The platform supports the requested Runtime API version.

It must not validate:

- Component count.
- File count.
- Whether charts come from a particular component library.
- Whether the page uses a fixed grid.
- CSS class names or directory naming conventions.
- Whether the Agent uses the platform's preferred internal architecture.

Static validation is not a security boundary. CSP, iframe isolation, the Data Gateway, and the Worker sandbox must still enforce network, filesystem, and data-access restrictions.

## 9. Preview Contract

Preview uses the current Draft build artifact and runs inside an isolated iframe.

```text
Agent modifies src
  → build_preview
  → build dist
  → Preview URL
  → refresh iframe
```

In preview mode:

- Queries use the current editor's restricted data permissions.
- `DashboardContext.mode` is `preview`.
- Build and Runtime errors are returned to the Agent.
- The management system displays file Diffs, Tool calls, and build status to preserve Coding Agent observability.

The management system does not implement preview by modifying source code, and it does not format or rewrite `src/` after preview. Preview queries and watchers use current authorized data; source-row changes do not require a Preview rebuild.

## 10. Saving and Publishing

The platform automatically stores a recoverable Draft Checkpoint after a successful Agent Job changes files. An explicit save promotes the current Draft into an immutable Revision and must preserve the original source generated by the Agent:

```text
Revision
├── dashboard.manifest.json
├── src snapshot
├── public snapshot
├── template version
└── build metadata
```

Publishing:

1. Builds from a specified Revision.
2. Runs Manifest, Query, and security validation.
3. Saves an immutable `dist/` artifact.
4. Pins immutable Query Revision bindings.
5. Records the relationship between the source Revision and published artifact.
6. Makes share links point to one fixed Published Revision.

The platform must not store only the compiled `dist/`. Preserving source enables continued Coding Agent edits, Diffs, rollbacks, and rebuilds.

Saving and publishing never freeze ordinary query results. A Publication is an immutable frontend artifact backed by live Data Gateway execution. Automatic or manual data refresh does not create a Dashboard Revision.

## 11. Security Boundaries and Source Freedom

The following restrictions do not reduce the core freedom of Vibe Coding:

| Restriction | Reason |
|---|---|
| May modify only the current dashboard Workspace | Tenant isolation |
| No direct database access | Credential and data security |
| Network requests must go through the Runtime/Data Gateway | Prevent data exfiltration |
| Only approved dependencies may be used | Build stability and supply-chain security |
| Must produce a standard entry point | Preview and publishing compatibility |
| Must declare Query IDs | Permission auditing and runtime validation |

These rules constrain only system boundaries. Inside `src/`, the dashboard remains an ordinary, complete frontend codebase that can be continuously refactored.

## 12. Lifecycle

```text
draft → validated → published → archived
```

- **draft**: The Coding Agent may continue modifying `src/` and the Manifest.
- **validated**: A specific Revision has passed build and boundary validation.
- **published**: An immutable published artifact has been generated.
- **archived**: External access is disabled while source and version history remain available.

Validation status belongs to a specific Revision. Further Draft changes require validation again before publishing.

## 13. First-Version Acceptance Criteria

Complete the following flow using a sample sales data source:

1. A user asks through conversation for a sales dashboard.
2. The Coding Agent freely creates multiple components, styles, and data-processing files.
3. The dashboard retrieves data through the Runtime API.
4. The Agent can refactor the layout or replace chart implementations through follow-up conversation.
5. `validate_dashboard` succeeds without parsing the component tree.
6. The Preview iframe renders correctly and supports interaction.
7. Full source and Diffs remain available after saving a Revision.
8. The published page calls only the Data Gateway, not Pi.
9. Source-row changes appear through runtime query or watcher refresh without rebuilding.
10. A share link always loads a fixed Published Revision.
11. The management system never converts `src/` into a low-code DSL.
